01

What I build

Most AI demos stop at the point where a person is still in the loop for every step. The work I care about starts there: making a system trustworthy enough to run a long task on its own and hand back a result you can check. That takes three things that don't come in the box.

Enforcement instead of instruction. A rule in a prompt is a request the model can drop under context pressure. The rules that matter live in hooks that block. My Stop hook will not let a session end after substantial work until a handoff document exists. A PreToolUse hook rejects any handoff filename with a hand-typed date, because the model kept confabulating tomorrow's date from a UTC clock. Neither rule depends on the model remembering it.

Pacing by measurement. Two hooks read how full the context window is (from the session log, against the model's real window size) and how many tool calls fired in the last sixty seconds. Parallel agent dispatch sizes each wave from those numbers and backs off before a rate limit, not after.

Less model, on purpose. A mature product moves work off the LLM and into deterministic code, so users spend fewer tokens and get the same answer twice. Every hook on this page is shell or Python with no model call. In my drone-tuning product, blackbox chirp detection and the parameter recommendations built on it are plain Python; a model narrates and interprets, it does not produce the recommendations.

I use Claude Code as the platform, and I use Anthropic's native features wherever they cover the need. What's on this page is the layer above them: the parts that make a capable model into a system I would leave running overnight.

Claude Code fires shell scripts at lifecycle points with structured JSON on stdin. This config wires seven. The wiring is published as settings.example.json in the repo.

Exit codes are asymmetric. exit 2 blocks and surfaces stderr to the model. exit 1 does not block. A hook meant to enforce a constraint must exit 2, and the failure direction has to be chosen per hook: a file-protection hook fails closed, a Stop hook fails open, because a Stop hook that fails closed wedges every session.

Matchers cover tool names, not file operations. Write|Edit misses every Bash write. Path protection has to include Bash and inspect the command string.

Review agents, in a fixed order

Named subagents are Markdown files with a model, a persona, and a job. Paced parallel work

The batch protocol (batchc) splits independent work into waves, dispatches each wave in parallel, and merges before the next. Wave size is not a constant. It reads the two measurements above: it caps at two tasks when the window is half full, one at three quarters, and pauses when the burst rate signals a throttle coming. When more than one file changed, a separate context has to run an independent review before the batch counts as done, and the Stop hook enforces that.

For fan-out that has to be deterministic, I use Claude Code's Workflow tool with scripts where the control flow is code. My research workflow caps itself at under thirty agents (the uncapped version spawns up to 97) so a deep run stays inside subscription rate limits; the two constants that set the cap are documented with their exact agent cost per increment.

L3Auto memory

Claude Code's native per-project memory, plus an anti-ratchet hook: each recorded belief carries when it was last challenged and by whom, and a stale one gets flagged for independent review at session start.

session start

Three tiers on three timescales. The middle one is the differentiator: curated, cross-project, and searchable.

Between sessions sits the handoff document: what was done, what is in flight, what the next session starts with. Two hooks guard it. One makes the filename timestamp impossible to hand-type; the other refuses to let a working session end without one. The next session reads the handoff, not the transcript.

The anti-ratchet hook came out of a clinical-reasoning project, where a working hypothesis had entrenched across sessions until an outside model caught it. The fix was metadata plus a hook, not a better prompt: the system now knows how long a belief has gone unchallenged and forces the challenge.

Where this sits next to native Claude Code

Anthropic ships fast. Hooks, custom subagents, auto memory, Remote Control, the Workflow tool, and cross-machine session messaging all arrived while this setup was in use, and I moved to the native version wherever it covered the need. I don't claim to have built any of those first; the changelog is public and the dates mostly precede my earliest verifiable commit.

The claim I do make is narrower and checkable. When I built the pieces below, the native equivalent was absent, a research preview behind an experimental flag, or changing weekly. Agent teams entered research preview behind an experimental flag in February 2026. More than half of Remote Control's changelog entries fall in August and September 2026. Knowing when to retire your own

In early 2026 I built a mobile command center on Discord: hooks that stream the model's narrative and every tool call to a channel, approvals that page me, and a keyword-dispatch hook so a dictated word triggers a slash command. Anthropic was building the same shape at the same time. Remote Control existed by February, channels shipped in March, push notifications in April. That is convergence, and I say so because anyone can check. Remote Control now handles the monitoring case and I use it. The streaming hooks are still published because sending every tool call to a channel is still not native, and because the judgment call of when to switch is the part worth showing.

05

Hardware on one machine, reasoning on another

Cross-machine session messaging (above) turns out to solve a problem that's specific to hardware: firmware tuning needs a live USB connection to a flight controller, but deciding what to do with what that connection reports doesn't need to happen on the same machine the drone is plugged into. Droneteleo now splits along that line — a small daemon on whichever machine has drones connected serves flight-controller access over Tailscale, while the Claude session doing the reasoning runs wherever I am, talking to that daemon's machine over one channel and to me over another.

In practice: hand a session the day's blackbox logs and a flight controller on a different machine, have it analyze and stage a fix, then close the laptop while it waits at the bench. The actual save still happens when I'm there to press it myself, because of how I've set the workflow up, not because the daemon enforces it. Or drive that same session from my phone with the laptop closed, through the same dictated-keyword relay already built for Discord.

Letting a model hold write access to a flight controller only works if the review discipline above survives contact with real hardware. It did, on the fourth try: the Safety Officer's first pass on this daemon was DO NOT SHIP — motor commands weren't blocked, and nothing stopped the motors on an unexpected disconnect. The next two rounds each found the prior fix incomplete: a command-injection bypass through an embedded carriage return, then a second through the byte (0x7F, DEL) Betaflight's own CLI reads as backspace. It closed for good only once the check became a whitelist read out of Betaflight's own firmware source, verified against two real flight controllers including an actual flash write and reboot.

The same loop is also how Droneteleo gets built with more than one flight controller or radio connected, not just how it gets operated afterward:

  • New command logic is exercised against a simulated flight controller first (mock_daemon_virtual_testing), so most iteration needs no hardware plugged in at all.
  • When two flight controllers or radios really are connected together, access to a shared serial port is explicitly serialized (serial_port_contention), not left to chance.
  • Nothing that could spin a motor ships without the Safety Officer's review, whose first question is always unexpected prop spin, and whose verdict has stopped a shipment before.
06

One harness, several model providers

Claude Code is the only agent harness I use, including for work that isn't running on an Anthropic model. Provider is fixed per process, not per subagent: a workflow script routes a task to ccx <target>, which launches a separate Claude Code process against GLM, Kimi, or DeepSeek's backend rather than switching providers inside a running session. It's opt-in per turn — nothing routes off Claude's own models unless I ask for it in that turn — and most of those targets are metered per token rather than flat-rate.

In my experience, this only became worth doing recently: OpenRouter has added sticky routing and prompt caching in the past several months, which is what keeps a metered call from re-paying full context cost every turn. That's true for the targets I reach through OpenRouter; the one flat-rate plan I pay for doesn't go through it.

Projects this runs

Most of these exist because the setup between a person and the thing they actually wanted to do is where they quit — and that part was never supposed to be the hard part.

Seven systems — six in real use, one a paused proof of concept — two of them public. The family-facing ones are built around my own household; a general version of either is possible and not started.

Agentic Roblox game development public

A live, monetized Roblox game built with an AI coding agent as the primary implementer. Published with about 40,000 lines of the actual Luau source, a permalinked code tour, and a candid account of what the agent structurally cannot do on a closed engine.

github.com/FJ-Oekstrahay/agentic-roblox-gamedev
Droneteleo private · in daily use

A command-line tool that holds a live USB connection to a Betaflight flight controller and lets a pilot tune it by describing the problem. Changes stage to RAM; nothing touches flash without an explicit save. A dedicated safety-review agent audits anything that could spin a motor, because on this project that risk was never theoretical. Chirp detection, its signal processing, and the parameter recommendations are deterministic Python; a model narrates and interprets, it doesn't produce the recommendations, and users pay for fewer tokens. Also the subject of the cross-machine and hardware-in-the-loop workflow above.

Retirement planning engine private · in daily use

A projection engine with a certified Monte Carlo core, a versioned decision registry, and a claims gate that checks every number in every report against its source before it ships. A synthetic-data design study shows how a spending dial interacts with a guaranteed floor.

Health reasoning system private · architecture publishable

A structured personal medical corpus reasoned over by specialty personas built to disagree with each other, under a three-question ordering gate and the anti-ratchet mechanism described above. Built for my own situation; the architecture generalizes and a public version is possible.

Family infrastructure private · in daily use

A Cloudflare Worker serving a shared family board, email and SMS intake workers feeding a structured wiki, event registration with a one-time-passcode gate, and a macOS screen-time daemon that had to work around the OS's own notification suppression. Built for my household; a general version is possible.

AI phone agent for prior authorization proof of concept · paused

Calls an insurer's line, navigates the IVR by tone injection, and conducts the authorization conversation. Before any live call it was red-teamed against a second model playing the insurer, which caught real domain gaps. Paused since April 2026; no Business Associate Agreement is in place, so no real patient data has flowed through it.

Bambu 3D-print settings tool public

Two Python scripts that turn an STL plus a plain-language part description into a ready-to-print .3mf, by treating the project file as what it is, a zip of JSON and XML, and patching it directly.
