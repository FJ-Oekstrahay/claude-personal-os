01

What I build

Most AI demos stop at the point where a person is still in the loop for every step. The work I care about starts there: making a system trustworthy enough to run a long task on its own and hand back a result you can check. That takes three things that don't come in the box.

Enforcement instead of instruction. A rule in a prompt is a request the model can drop under context pressure. The rules that matter live in hooks that block. My Stop hook will not let a session end after substantial work until a handoff document exists. A PreToolUse hook rejects any handoff filename with a hand-typed date, because the model kept confabulating tomorrow's date from a UTC clock. Neither rule depends on the model remembering it.

Pacing by measurement. Two hooks read how full the context window is (from the session log, against the model's real window size) and how many tool calls fired in the last sixty seconds. Parallel agent dispatch sizes each wave from those numbers and backs off before a rate limit, not after.

Less model, on purpose. A mature product moves work off the LLM and into deterministic code, so users spend fewer tokens and get the same answer twice. Every hook on this page is shell or Python with no model call. In my drone-tuning product, blackbox chirp detection and the parameter recommendations built on it are plain Python; a model narrates and interprets, it does not produce the recommendations.

I use Claude Code as the platform, and I use Anthropic's native features wherever they cover the need. What's on this page is the layer above them: the parts that make a capable model into a system I would leave running overnight.

The system

Hook lifecycle

Claude Code fires shell scripts at lifecycle points with structured JSON on stdin. This config wires seven. The wiring is published as settings.example.json in the repo.

Exit codes are asymmetric. exit 2 blocks and surfaces stderr to the model. exit 1 does not block. A hook meant to enforce a constraint must exit 2, and the failure direction has to be chosen per hook: a file-protection hook fails closed, a Stop hook fails open, because a Stop hook that fails closed wedges every session.

Matchers cover tool names, not file operations. Write|Edit misses every Bash write. Path protection has to include Bash and inspect the command string.

Review agents, in a fixed order

Named subagents are Markdown files with a model, a persona, and a job. The four reviewers are the ones that change outcomes, and the order they run in is a rule, not a preference: the product skeptic runs before the technical planner, because once a planner has produced a plan, every later critique anchors on it.

Seven named subagents, grouped by job. Each file sets a default model, and the dispatcher overrides it when a task calls for more; a CTO review of a hard plan often runs on Opus.

Paced parallel work

The batch protocol (batchc) splits independent work into waves, dispatches each wave in parallel, and merges before the next. Wave size is not a constant. It reads the two measurements above: it caps at two tasks when the window is half full, one at three quarters, and pauses when the burst rate signals a throttle coming. When more than one file changed, a separate context has to run an independent review before the batch counts as done, and the Stop hook enforces that.

For fan-out that has to be deterministic, I use Claude Code's Workflow tool with scripts where the control flow is code. My research workflow caps itself at under thirty agents (the uncapped version spawns up to 97) so a deep run stays inside subscription rate limits; the two constants that set the cap are documented with their exact agent cost per increment.

Other providers, same harness

Some work runs on GLM, Kimi, or DeepSeek rather than an Anthropic model, and Claude Code is still the only harness. The provider is fixed per process, so a workflow script routes such a task to ccx <target>, a separate Claude Code process against that backend. Those workers don't get a worktree of their own the way Claude-tier ones do, because they really are a different process. Except for one flat-rate plan that skips OpenRouter, the targets are metered per token, so the routing is something I opt into per turn. A metered call is only affordable because OpenRouter caches the prompt and pins a session to one node; without that, every turn re-pays the full context.

Memory that survives the session

L1Rules

CLAUDE.md, loaded every session. Standing orders, the code-quality gate, verification disciplines, lessons that must be true every time.

always loaded
L2Playbooks

More than 450 curated entries in a private repo cloned on both machines. Each records what broke, why, and how to apply it. Indexed for semantic search across every project.

semantic recall
L3Auto memory

Claude Code's native per-project memory, plus an anti-ratchet hook: each recorded belief carries when it was last challenged and by whom, and a stale one gets flagged for independent review at session start.

session start

Three tiers on three timescales. The middle one is the differentiator: curated, cross-project, and searchable.

Between sessions sits the handoff document: what was done, what is in flight, what the next session starts with. Two hooks guard it. One makes the filename timestamp impossible to hand-type; the other refuses to let a working session end without one. The next session reads the handoff, not the transcript.

The anti-ratchet hook came out of a clinical-reasoning project, where a working hypothesis had entrenched across sessions until an outside model caught it. The fix was metadata plus a hook, not a better prompt: the system now knows how long a belief has gone unchallenged and forces the challenge.

Knowing when to retire your own

Claude Code had no way to run sessions from my phone, so I built a mobile command center on Discord: hooks that stream the model's narrative and every tool call to a channel, approvals that page me, and a keyword-dispatch hook so a dictated word triggers a slash command. Anthropic has since shipped Remote Control, channels, and push notifications. Remote Control now handles the monitoring case and I use it. The streaming hooks are still published because sending every tool call to a channel is still not native, and keyword dispatch by dictation is a pattern worth copying.

05

Hardware on one machine, reasoning on another

Claude Code can now message a session on another machine natively, which turns out to solve a problem that's specific to hardware: firmware tuning needs a live USB connection to a flight controller, but deciding what to do with what that connection reports doesn't need to happen on the same machine the drone is plugged into. Droneteleo splits along that line. A small daemon on whichever machine has drones connected serves flight-controller access over Tailscale, while the Claude session doing the reasoning runs wherever I am, talking to that daemon's machine over one channel and to me over another.

Connected, disconnected, reconnected

  1. Connected. The drone is plugged into the bench machine; the session runs on another. It takes the day's blackbox logs, either handed over by me or read straight from the controller's flash, and confirms the rate profile and parameters are set the way I want.
  2. Disconnected. Drone unplugged, laptop closed. The session analyzes the logs and stages a fix. It is reachable from my phone in this state, through the same dictated-keyword relay already built for Discord, so I can check what it found or redirect it.
  3. Reconnected. I review what it staged. The actual save still happens when I'm there to press it myself; that's a workflow choice, not something the daemon enforces.

Building it with hardware attached

Claude also does Droneteleo's own development with real flight controllers and radios connected, more than one at a time. What makes that workable is already on this page.

  • New command logic is exercised against a simulated flight controller first (mock_daemon_virtual_testing), so most iteration needs no hardware plugged in at all.
  • When two flight controllers or radios really are connected together, access to a shared serial port is explicitly serialized (serial_port_contention), not left to chance.
  • Nothing that could spin a motor ships without the Safety Officer's review, whose first question is always unexpected prop spin. Letting a model hold write access to a flight controller only works if that review survives contact with real hardware. It did, on the fourth try: the first pass on this daemon was DO NOT SHIP, because motor commands weren't blocked and nothing stopped the motors on an unexpected disconnect. The next two rounds each found the prior fix incomplete: a command-injection bypass through an embedded carriage return, then a second through the byte (0x7F, DEL) Betaflight's own CLI reads as backspace. It closed for good only once the check became a whitelist read out of Betaflight's own firmware source, verified against two real flight controllers including an actual flash write and power-cycle reboot.

Projects this runs

Most of these exist to take the setup off the front of something, so a person who isn't an expert yet gets to the part they came for.

Seven systems here: six in daily use, one paused proof of concept, two of them public. The family-facing ones are built around my own household. A general version of either is possible; neither is built.

Agentic Roblox game development public

A live, monetized Roblox game built with an AI coding agent as the primary implementer. Published with about 40,000 lines of the actual Luau source, a permalinked code tour, and a candid account of what the agent structurally cannot do on a closed engine. It started as a way to build a game with my kid without either of us learning an engine's project structure first.

github.com/FJ-Oekstrahay/agentic-roblox-gamedev
Droneteleo private · in daily use

A command-line tool that holds a live USB connection to a Betaflight flight controller and lets a pilot tune it by describing the problem, so a new pilot doesn't have to learn a PID table before the quad flies well. Changes stage to RAM; nothing touches flash without an explicit save. A dedicated safety-review agent audits anything that could spin a motor, because on this project that risk was never theoretical. Chirp detection, its signal processing, and the parameter recommendations are deterministic Python; a model narrates and interprets, it doesn't produce the recommendations, and users pay for fewer tokens. Also the subject of the cross-machine and hardware-in-the-loop workflow above.

Retirement planning engine private · in daily use

Most retirement tools aim for the largest possible balance at the end. This one optimizes for quality of life in the early, active years of retirement while keeping financial security intact for the full duration. Underneath is a projection engine with a certified Monte Carlo core, a versioned decision registry, and a claims gate that checks every number in every report against its source before it ships. A synthetic-data design study shows how a spending dial interacts with a guaranteed floor.

Health reasoning system private · architecture publishable

A structured personal medical corpus reasoned over by clinical personas built to disagree with each other, among them a longevity-first physician, a pragmatic practicing clinician, and an endocrinologist. They work under a three-question ordering gate and the anti-ratchet mechanism described above, and do the gathering and cross-checking up front, before anyone has to decide anything. Built for my own situation; the architecture generalizes and a public version is possible.

Family infrastructure private · in daily use

A Cloudflare Worker serving a shared family board, email and SMS intake workers feeding a structured wiki, event registration with a one-time-passcode gate, and a macOS screen-time daemon that had to work around the OS's own notification suppression. Built so a school signup or a shared calendar doesn't depend on a parent reconciling five different inboxes by hand; a general version is possible, not yet built.

AI phone agent for prior authorization proof of concept · paused

Prototyped in collaboration with a physician. Calls an insurer's line, navigates the IVR by tone injection, and conducts the authorization conversation. Before any live call it was red-teamed against a second model playing the insurer, which caught real domain gaps. Currently paused; no Business Associate Agreement is in place, so no real patient data has flowed through it.

Bambu 3D-print settings tool public

Two Python scripts that turn an STL plus a plain-language part description into a ready-to-print .3mf, by treating the project file as what it is, a zip of JSON and XML, and patching it directly. A first print used to cost an hour in slicer settings before anything came off the bed. These days I ask Claude for thicker walls, a different infill, or a solid panel turned into a mesh screen, and get a file back. The published scripts cover the settings side; the geometry edits are newer and not in the public repo yet.
